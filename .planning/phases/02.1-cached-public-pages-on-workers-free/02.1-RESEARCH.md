### Gateway (default fetch entrypoint, Workers Cache off)
- **D-10 Hard deny.** These go straight to OpenNext and are never cacheable: `/admin*`, `/<locale>/admin*`, `/auth/callback`, `/api/*`, non-GET/HEAD requests, any `next-action` header, and `/<locale>/auth*` **for the signed-in class only**.
- **D-11 Bare `/` and unprefixed paths.** The gateway answers a 307 to `/<locale><path><query>`. The locale is the NEXT_LOCALE cookie if it is en/ar, else Accept-Language negotiation, else en. The proxy is not invoked and the redirect is not cached. Excluded: `/api`, `/auth/callback`, `/_next`, files with an extension, `sitemap.xml`, `robots.txt`.
- **D-12 Verified class.** The gateway rebuilds the Supabase auth cookie (chunked `.0/.1`, `base64-` prefix) and verifies the JWT locally: ES256 against the project JWKS, cached per isolate, the same check as `getClaims()`.
  - Valid → `user`.
  - Auth cookie present but invalid, expired or unverifiable → bypass to OpenNext, where the proxy refreshes or clears it.
  - Only `sb-…-code-verifier`, or no auth cookie → `anon`.
  - Cookie presence alone never makes `user`.
- **D-13 Key.** `cf.cacheKey = /__c/<class>/<rsc-kind>/<segment-prefetch>/<path>?<allowlisted params sorted>`.
  - `_rsc` is stripped.
  - `utm_*`, `fbclid`, `gclid` and `msclkid` are removed from the URL itself before the render, so no stored body or `Location` carries a visitor's query (this fixes the e49a219 308 bug).
  - `next` (auth) is kept only when `getSafeAuthNextPath` accepts it, and `category` (browse) only when it passes its sanitizer; any other value bypasses.
  - No device dimension.
- **D-14 Strip.** For cacheable requests the gateway removes `Cookie`, `Authorization` and `Accept-Language` before calling the cached entrypoint. It sets `x-clickit-class: user|anon` and drops any inbound copy of that header. On that path the proxy's gates read only the class header.

### Cached entrypoint (OpenNext behind `ctx.exports`, Workers Cache on)
- **D-20** Cacheable responses carry `Cache-Control: max-age=<long>, stale-while-revalidate, stale-if-error` and `Cache-Tag`. Everything else is `no-store`.
- **D-21** The `user` class never stores redirects. Gate 307s are cached only for `anon`.
- **D-22 Fill on Free.**
  - Fills run in the cached entrypoint's own invocation.
  - Content saves use `ctx.cache.invalidate()` (stale-while-revalidate), not purge, so the old copy is served until a refill succeeds, indefinitely. `stale-if-error` covers a refill that ends in 1102.
  - Public pages are prerendered at build (`generateStaticParams`, ISR entries populated at deploy) so most fills are a cache read plus the proxy.
  - A post-deploy seeding script, run by the controller, fills the version-keyed cache: every URL × class × locale, retried until it is served from the cache.
- **D-23 Freshness.**
  - Invalidation is by content tags only: `site-config`, `shows`, `episodes`, `shorts`, `seasons`, `categories`, and the FAQ/legal `revalidatePath` calls. `profile/actions.ts` does not invalidate shared entries.
  - The coming-soon toggle (`updateFeatureFlags` → `bumpSiteConfigCache`) purges instead of invalidating, so it takes effect at once.
  - Invalidations are debounced: Workers Cache uses the Free purge limit of 5 tag requests a minute per account.
- **D-24** No `cookies()`, `headers()` or server Supabase client in any cached route's import graph. A test enforces it.

- **D-31 Loading look, signed by Koss** (`.planning/debug/cpu-public-cache-mockup.html`):

- **D-33 Session refresh.** The browser client (`createBrowserClient`, auto-refresh) refreshes before expiry. An expired JWT bypasses to the proxy for refresh.

### Tests (named, required)
- **D-40** These tests are required:
  - **Forged and invalid cookies.** A forged `Cookie: sb-x=1` gets anon. A JWT signed with another key bypasses. Neither ever gets the user shell or a cached `/watch/<episode>` body.
  - **Expired JWT** with a valid signature: bypass to the proxy, not cached.
  - **Code-verifier cookie only:** anon.
  - **Admin and non-admin signed in:** the same viewer shell; `/admin*` is never cached; the Admin menu entry comes from the browser.
  - **Redirects:** none stored in class `user`. Anon 307s are stored, and the coming-soon toggle purges them.
  - **Hard-deny list:** always OpenNext, `no-store`.
  - **Poisoning:** the same URL with varied Accept-Language, Cookie, User-Agent, X-Forwarded-Host, Forwarded and Next-Url gives an identical body before a route joins the cache.
  - **Byte-identical anon HTML:** two different anon requests get byte-identical HTML apart from the allowed key parts (controller condition).
  - **RTL:** a stored /ar body has `lang="ar" dir="rtl"`, a stored /en body `lang="en" dir="ltr"`.
  - **Bare and unprefixed paths:** a 307 by cookie, then Accept-Language, then en; not cached; proxy not invoked.
  - **Query handling:** `_rsc` is stripped; utm is absent from stored bodies and `Location` headers.
  - **Import graph:** no `cookies()`, `headers()` or server Supabase client in cached routes.
  - **Invalidation scope:** a profile action does not invalidate shared entries; a content action does.
  - **Long session:** local Supabase with a 60 s JWT, two tabs, 15 minutes of mixed cached and bypassed pages. The user stays signed in, with no `refresh_token_already_used`.

## Summary

The design in CONTEXT.md is implementable, with eleven findings that sharpen it and four that need a decision before planning (listed next). The core mechanism is documented and, in the parts that are checkable offline, consistent with the installed source: wrangler 4.151.2 accepts `cache` and per-entrypoint `exports` (local scratch test, verified), `ctx.exports.<Name>.fetch(req, { cf: { cacheKey } })` works in workerd 1.20261019.1, and the Workers Cache docs describe gateway-with-cache-off in front of a cache-on entrypoint as the supported pattern. What cannot be checked offline: the cache itself (workerd has `ctx.cache` as `undefined` and does not cache; the local preview cannot show hits, invalidate or purge), and every Free-plan counting rule (hits, the gateway-to-entrypoint call, static assets against the 100k/day request cap; whether the 10 ms CPU budget is per invocation or summed across the two). Spike (e) is therefore the real go/no-go and must be measured, not inferred.

The biggest levers for fill success on Free are (1) `enableCacheInterception: true`, which in `routingHandler.js` runs after the proxy/middleware (so gates stay in force; the comment in `open-next.config.ts` saying it could skip the gates is wrong) and serves prerendered HTML/RSC/segment entries from the R2 incremental cache without loading the Next server bundle, and (2) making the pages genuinely static so those entries exist. Without (2) there is nothing to intercept; today `.next/prerender-manifest.json` has only `/_global-error`, `/_not-found`, `/robots.txt`, `/sitemap.xml` [VERIFIED: local build output].

**Primary recommendation:** Build the gateway as a pure, node-testable module (`src/server/gateway/*.ts`, erasable TS, relative `.ts` imports) with a thin `custom-worker.ts` that exports `default` (gateway, cache off), `Pages extends WorkerEntrypoint` (OpenNext behind a lazy dynamic import, cache on) and `DOQueueHandler`. Make Plan 1 (spike) prove the five unknowns on workers.dev with a purpose-built probe route set before any page refactor starts, and write down the Free counting answers in the spike report.

### Findings that sharpen or contradict locked decisions (reported, not changed)

| # | Finding | Touches | Impact |
|---|---------|---------|--------|
| F1 | **Invalidate/purge are scoped to the calling entrypoint.** Server actions run in the default (gateway) invocation via the hard-deny path, so `ctx.cache.invalidate` there targets the gateway's (disabled) cache. The call must be an RPC method on the cached class: `ctx.exports.Pages.invalidate({ tags })`. | D-22, D-23, D-03(e) | Plan must add an RPC method, a wrapper used by every admin/cron revalidation site, and a coverage test. |
| F2 | **`_rsc` and the state-tree headers must NOT be stripped from the request that reaches Next.** `validateRSCRequestHeaders: true` (default, in the installed build) makes Next 307 to `?_rsc=<hash>` when `_rsc` does not match the header hash. Strip `_rsc` from the cache key only. And OpenNext emits `Vary: RSC, Next-Router-State-Tree, Next-Router-Prefetch, Next-Router-Segment-Prefetch, Next-Url`; Workers Cache stores a variant per distinct header value, so `Vary` must be removed on the cached entrypoint's response (re-added by the gateway for browsers). | D-13, D-14, D-03(a) | Otherwise one cache entry per state-tree value, or a cached 307 loop. |
| F3 | **`Set-Cookie` bypasses Workers Cache.** next-intl `syncCookie` sets `NEXT_LOCALE` on any response when the request has no NEXT_LOCALE and Accept-Language resolves to a different locale than the URL: with Cookie/Accept-Language stripped, every `/ar/*` response sets it. Also `Link` (hreflang, built from the request host) and absolute `Location` headers carry the first requester's host while the key excludes Host. The Pages wrapper must drop `Set-Cookie`, `Link`, rewrite same-origin `Location` to a relative path; the gateway re-adds `NEXT_LOCALE` itself. | D-12, D-14, D-21 | Without it `/ar` never caches. |
| F4 | **`s-maxage` disables stale-while-revalidate and stale-if-error** at Workers Cache. OpenNext emits `s-maxage=…, stale-while-revalidate=…`. The wrapper must replace `Cache-Control` with `public, max-age=…, stale-while-revalidate=…, stale-if-error=…`, and the gateway must send browsers a non-storing `Cache-Control` (the stored long max-age must not reach the browser). | D-20, D-22 | Silent loss of the "serve stale until refill" guarantee. |
| F5 | **Time-based ISR leaks in through `unstable_cache`.** Next lowers a page's revalidate to the smallest `revalidate` of any `unstable_cache` it reads (`unstable-cache.js` lines 115-122). `getAppConfig` is 900 s and sits in the layout, so every page would get `revalidate: 900` and the DO queue would re-render it in the background (a fill-sized CPU hit per URL per 15 min, and 100k/day). D-23 ("tags only") needs `revalidate: false` on the caches used by static routes, plus cron-driven tag updates for scheduled publishing. | D-22, D-23 | Check `initialRevalidateSeconds` in `.next/prerender-manifest.json` after the first static build. |
| F6 | **Pages that read `searchParams` cannot be static** (auth `next`, updates `show`, watch `category`, browse `category`). D-13 keeps `next` and `category` in the key, which implies server rendering per value. Either read them in the browser (`useSearchParams` under Suspense; then the HTML is identical for every value and the key drops them) or accept a non-prerendered dynamic fill for `/watch?category=`. Recommended: browser read for `next`, `show`, `category`. | D-13, D-30 | Decide in plan 2; affects the key allowlist and seeding. |
| F7 | **How the class reaches the render is unspecified.** D-24 forbids `headers()` in cached routes, yet UI-SPEC says signed-out first paint is the Sign In button and signed-in first paint is the empty avatar circle. One prerendered HTML cannot know the class. Options: (B, recommended) one HTML plus a tiny inline pre-paint script (CSP already allows `'unsafe-inline'`) that reads cookie presence and sets `<html data-signed-in>`; CSS shows the circle or the Sign In control. (A) class-variant routes via a `next.config` `rewrites()` header condition and a `[cls]` segment. B keeps one HTML per path, makes ISR HEAD revalidations correct (they carry no class), and needs no route-tree change. | D-24, D-30, D-31 | Needs a signed decision; see Open Question 1. |
| F8 | **The DO queue's revalidation request goes to the gateway.** `DOQueueHandler` fetches `https://<host><path>` with `HEAD`, `x-prerender-revalidate`, `x-isr: 1` through `WORKER_SELF_REFERENCE`, which is the default entrypoint. The gateway must send any request with those headers straight to OpenNext (add to D-10) and never cache it. HEAD is cacheable at Workers Cache ("GET and HEAD share an entry"), so this matters. | D-10 | Silent revalidation failures otherwise. |
| F9 | **Locale roots for the signed-in class.** `/<locale>` is a proxy 308 (d43fd90). D-21 forbids storing redirects for `user`, so every signed-in `/en` costs a full OpenNext invocation (proxy 15-30 ms), above the 10 ms goal. The gateway can answer the 308 itself for both classes with the pure `localeRootTarget()` (no render, no cache). Behaviour change: with coming-soon on, `/en` becomes 308 then 307 instead of one 307. | D-11, D-21 | Small, recommended; needs Koss's nod as a behaviour change. |
| F10 | **Deploy warning explanation.** `scripts/cf/deploy.mjs` runs `opennextjs-cloudflare deploy`, whose populate-cache step calls wrangler `getPlatformProxy` with the project config (`node_modules/@opennextjs/cloudflare/dist/cli/commands/utils/helpers.js`): a proxy with no script loaded cannot export any DO class, so workerd prints the "no such class is exported" warning. OpenNext's known-issues page calls it ignorable. This is evidence the warning is not about the deployed script; it is not proof ISR revalidation works (spike d must still run it). | D-03(d) | Likely harmless; still verify by tail. |
| F11 | **Free-plan counting is the open risk.** Pricing: "When Workers Caching is enabled, requests served from the Worker's cache are billed at the same per-request rate as requests that invoke the Worker"; static asset requests and worker-to-worker calls "normally free, are billed at the standard request rate" once caching is enabled; service-binding CPU is "the total CPU time used across both Workers". None of that says how Free's 100k/day and 10 ms are applied. Enable caching per entrypoint only (no top-level `cache`) and measure assets, hits and the exports call. | D-03(e) | A page view could cost 2 to 40 requests; the whole approach depends on it. |

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Visitor class (user/anon/bypass), hard-deny, bare-path 307, key build, header strip | Gateway Worker (default entrypoint, edge) | - | Must run before any render and cost under 10 ms; it is the only tier allowed to read cookies |
| Cache storage, SWR, stale-if-error, tags | Workers Cache (platform) | Pages entrypoint headers | Documented as the cache in front of a Worker entrypoint |
| Gates (coming-soon, auth), locale routing on fills | OpenNext middleware (`src/proxy.ts`), Pages entrypoint | - | Existing logic; on the cached path it reads only `x-clickit-class` |
| Static HTML / RSC / segment payloads | R2 incremental cache via OpenNext interception, built at deploy | Next server for runtime fills | Prerendered at build, read at fill time without loading the Next server |
| Personal state (avatar, watchlist, like, progress, resume, continue-watching, email prefill) | Browser (Supabase browser client + RLS) | - | The render is user-independent by D-24 |
| Session refresh | Browser (`createBrowserClient` auto-refresh) | Proxy on bypass (expired token) | Hits skip rotation by design (D-33) |
| Invalidation of shared entries | Pages entrypoint RPC method (`ctx.cache`) called from server actions in the default invocation | Next `updateTag`/`revalidatePath` for the R2/D1 side | `ctx.cache` is scoped to the calling entrypoint |
| Admin, actions, `/auth/callback`, `/api`, crons | OpenNext via default entrypoint, never cached | - | Out of scope, stays over 10 ms |

### Pattern 2: Gateway and cached entrypoint in one module
```ts
// custom-worker.ts (shape; Source: Workers Cache cache-keys docs + OpenNext custom-worker how-to)
import { WorkerEntrypoint } from 'cloudflare:workers'
import { handleGateway } from './src/server/gateway/index.ts'
export { DOQueueHandler } from './.open-next/.build/durable-objects/queue.js'   // keep: ISR queue

let openNext: Promise<{ fetch(r: Request, e: unknown, c: unknown): Promise<Response> }> | null = null
const load = () => (openNext ??= import('./.open-next/worker.js').then((m) => m.default))   // lazy: 2.6 MB middleware bundle

export class Pages extends WorkerEntrypoint {
  async fetch(request: Request) {
    const res = await (await load()).fetch(request, this.env, this.ctx)   // this.ctx = real ctx (cache, exports, waitUntil)
    return normalisePagesResponse(request, res)                              // F2, F3, F4
  }
  // RPC methods are NOT cached and run in this entrypoint, which is what scopes the purge correctly
  async invalidate(opts: { tags?: string[]; pathPrefixes?: string[] }) { return this.ctx.cache.invalidate(opts) }
  async purge(opts: { tags?: string[]; pathPrefixes?: string[]; purgeEverything?: boolean }) { return this.ctx.cache.purge(opts) }
}

export default {
  fetch: (request: Request, env: unknown, ctx: any) => handleGateway(request, env, ctx, { load }),
  scheduled: /* unchanged */,
}
```
Facts behind it: purges are "scoped to the calling entrypoint" [CITED: workers/cache/examples/, blog.cloudflare.com/workers-cache/], the Cloudflare blog's own example is `ctx.exports.CachedBackend.invalidate(userId)` [CITED], custom RPC methods "always run" and are not cached [CITED: limitations]. `ctx.cache` exists in the workerd binary (CacheContext, options `tags`, `pathPrefixes`, `purgeEverything`) but is `undefined` in local workerd [VERIFIED: strings of `@cloudflare/workerd-darwin-arm64/bin/workerd`; scratch test printed `ctxCache: "undefined"` and `{"threw":"…reading 'invalidate'"}`]. Every use needs a guard (`ctx.cache?.invalidate`) so the local preview and unit tests do not throw. Both `import { cache } from 'cloudflare:workers'` and `ctx.cache` are documented [CITED].

OpenNext hands the real `ctx` to server code: `getCloudflareContext().ctx` is whatever was passed to `handler.fetch(request, env, ctx)` (`templates/init.js`: `cloudflareContextALS.run({ env, ctx, cf: request.cf }, handler)`) [VERIFIED]. So the gateway must pass the real ExecutionContext, not a wrapper, for `ctx.exports` to be reachable from server actions.

### Pattern 3: Verified class (mirror of `getClaims`)
```ts
// Source: node_modules/@supabase/auth-js/dist/main/GoTrueClient.js getClaims (L4781-4844), lib/helpers.js getAlgorithm,
//         node_modules/@supabase/ssr/dist/main/{cookies.js,utils/chunker.js}
// Cookie: name = `sb-${new URL(SUPABASE_URL).hostname.split('.')[0]}-auth-token` (supabase-js SupabaseClient L369);
//   value = `base64-` + base64url(JSON.stringify(session)); if encodeURIComponent(value).length > 3180 it is split
//   into name.0, name.1, ... (raw pieces); reading tries the plain name first, then .0 .1 ... until a gap.
// Not an auth cookie: `${name}-code-verifier` (does not match name or name.N).
// JWT: alg must be exactly ES256 (anything else -> bypass, like getClaims' HS* fallback to getUser), kid in JWKS,
//   signature = raw r||s which is what Web Crypto expects, verify over `${rawHeader}.${rawPayload}`,
//   exp > now (validateExp), require non-empty `sub` (proxy uses claims.sub as userId).
const ES256 = { name: 'ECDSA', namedCurve: 'P-256', hash: { name: 'SHA-256' } }
const key = await crypto.subtle.importKey('jwk', jwk, ES256, true, ['verify'])        // cache the CryptoKey per kid
const ok = await crypto.subtle.verify(ES256, key, signature, new TextEncoder().encode(`${h}.${p}`))
```
JWKS: `GET ${SUPABASE_URL}/auth/v1/.well-known/jwks.json`; auth-js caches 10 min (`JWKS_TTL`) [VERIFIED]; the live project answers one ES256/P-256 key, kid `037f719c-…`, `cache-control: public, max-age=600`, public endpoint, no key needed [VERIFIED: curl 2026-10-21]; the local stack (port 55321) also serves an ES256 JWKS, so the gateway can be tested end to end locally [VERIFIED]. Unknown `kid`: refetch at most once per 60 s per isolate (otherwise forged kids amplify into subrequests).

CPU: a local workerd scratch run measured about 0.03 ms for verify and 0.04 ms for import plus verify (200 iterations; workerd's clock is coarse, so treat as "tens of microseconds") [VERIFIED local; ASSUMED the same order on Cloudflare hardware]. The expected gateway total of 0.5-2 ms in the plan is therefore dominated by cookie parse plus base64/JSON of a 2-3 KB session, not by crypto.

The gateway needs the Supabase URL and cookie name, but `.open-next/cloudflare/next-env.mjs` is empty (NEXT_PUBLIC values are inlined at build, not env) [VERIFIED]. Generate `.open-next/clickit-gateway-config.json` from the same env file in `scripts/cf/build-target.mjs` (public values only; the existing stamp stores hashes, so add a separate file) and import it statically in `custom-worker.ts`. ### Pattern 4: Invalidation from server actions
```ts
// src/server/edge-cache.ts (shape)
import { getCloudflareContext } from '@opennextjs/cloudflare'
export async function invalidateEdge(tags: string[]) {
  const { ctx } = getCloudflareContext()
  const pages = (ctx as any).exports?.Pages
  if (!pages) return { skipped: true }                                  // local preview / next dev
  const r = await pages.invalidate({ tags })                            // RPC into the cached entrypoint
  if (!r?.success) console.error('edge invalidate failed', r?.errors)   // Free: 5 requests/min per account, bucket 25
  return r
}
```
Order in an action: `updateTag(...)`/`revalidatePath(...)` first (R2/D1 side marks the ISR entry expired), then `invalidateEdge(tags)`, so the refill that follows regenerates from fresh data. Results carry `success` and `errors[{code,message}]`; rate limited calls return `success: false` [CITED: workers/cache/purge/]. Free limits are "5 requests per minute, bucket size 25, max operations per request 100" per account [CITED: developers.cloudflare.com/cache/how-to/purge-cache/]. One call per action with a deduplicated tag array is enough for two admins; a DO-alarm debouncer is only needed if the spike sees 429s (recommendation; Claude's discretion). Use a finite `max-age` backstop (suggest 24 h) so a failed or rate-limited invalidation self-heals; stale-while-revalidate and stale-if-error get a large window (maximum allowed value unconfirmed; spike e).

OpenNext offers no usable hook: `D1NextModeTagCache` has no `getPathsByTags`, so `revalidateTag` never calls `cdnInvalidation.invalidatePaths`; `writeTags` calls `purgeCacheByTags`, hard-wired to the zone purge API (`CACHE_PURGE_ZONE_ID`, `CACHE_PURGE_API_TOKEN`, or the `NEXT_CACHE_DO_PURGE` DO) [VERIFIED: `dist/api/overrides/internal.js`, `tag-cache/d1-next-tag-cache.js`]. Do not try to ride on it.

There are about 70 `updateTag`/`revalidatePath` call sites in `src/app/[locale]/admin/actions.ts` plus `publish-scheduled`, `profile/actions.ts` and `contact.ts` (grep, 2026-10-21). Route them through one module that records tags and flushes once (`runAdminAction`'s `revalidate` hook already exists for the YouTube actions), and add a source-scan test that fails when a call site is not covered. `profile/actions.ts:130` `revalidatePath('/', 'layout')` ("refresh navbar avatar") invalidates every ISR entry on any avatar change; it must go (D-23).

### Pattern 5: Normalising the Pages response (F2-F4)
```ts
// Cacheable (200, GET/HEAD, html|rsc|segment, path on allowlist, class anon, or class user and not a redirect):
//   Cache-Control: public, max-age=86400, stale-while-revalidate=2592000, stale-if-error=2592000   (values: discretion)
//   Cache-Tag: <tags for the route>            (Cache-Tag: comma separated, <=1024 chars each, <=1000, silently dropped if invalid)
//   delete Vary, Set-Cookie, Link; Location -> relative; add x-clickit-filled-at (stored with the body: a HIT shows an old value)

```
Use `private`/`no-store` (documented as BYPASS) for anything that must not be stored; "no-cache" stores and revalidates every time, which is not what is wanted.

### Anti-Patterns to Avoid
- **Stripping `_rsc`, `next-router-state-tree` or `next-url` from the forwarded request** (F2). Strip only from the key.
- **Trusting `x-next-cache-tags` for `Cache-Tag`.** OpenNext's interceptor deletes it from the served meta headers (`utils/cache.js` `getTagsFromValue`). Derive tags in the wrapper (Pitfall 9).
- **Calling `ctx.cache` from the default entrypoint** (F1).
- **Putting `headers()`/`cookies()` back into a layout "just for the class"** (F7). It silently turns the route dynamic and the import-graph test catches it.
- **A top-level `cache.enabled: true`** until F11 is measured.
- **Calling `getTranslations`/`getLocale` (next-intl) in `generateMetadata` without an explicit `{ locale }`.** Without `setRequestLocale` having run, next-intl reads `headers()` (`RequestLocale.js`: `getCachedRequestLocale() || await headers().get('X-NEXT-INTL-LOCALE')`) and the route goes dynamic.

## RSC and segment payloads (item 2)

- **Independent of the state tree for static routes** [VERIFIED: `node_modules/next/dist/build/templates/app-page-runtime.js`]: line 431 `if (!routeModule.isDev && !isDraftMode && isSSG && isRSCRequest && !isDynamicRSCRequest) stripFlightHeaders(req.headers)`; `FLIGHT_HEADERS` = `rsc`, `next-router-state-tree`, `next-router-prefetch`, `next-hmr-refresh`, `next-router-segment-prefetch` (`client/components/app-router-headers.js`). The segment header is read first (L337) and answered from `cachedData.segmentData.get(segmentPrefetchHeader)` (L1306-1330), else an empty 404. `next-url` is not in the strip list but is only used by intercepting routes; the app has none (`find src/app -name '(.)*' -o -name '@*'` is empty). `isSSG` is true when the route is in the prerender manifest. Spike (a) still diffs real payloads, but the code says they are identical. Anything that is NOT `isSSG` (dynamic fills, searchParams pages, PPR, which is off) does use the state tree.
- **Interception path**: `getBodyForAppRouter` in `@opennextjs/aws/dist/core/routing/cacheInterceptor.js` serves `cachedValue.rsc` for `rsc: 1` and `segmentData[<next-router-segment-prefetch>]` when that header is set; it returns `undefined` (falls to the server) when the segment is not present, and ignores the state tree entirely.
- **Order**: `routingHandler.js` runs `handleMiddleware` (the proxy) first, then rewrites, then `cacheInterceptor` (only when `dangerous.enableCacheInterception`). Gates therefore always run; interception only replaces the Next server render [VERIFIED]. Interception skips when the request has `next-action`, `x-prerender-revalidate`, a non-GET/HEAD method, preview cookies, or the key is not in the prerender manifest. It does not validate `_rsc`.
- **`_rsc`** is a cache-busting hash of (`next-router-prefetch`, `next-router-segment-prefetch`, `next-router-state-tree`, `next-url`) added by the client; with `experimental.validateRSCRequestHeaders` (default true, present in the installed build config) the Next server compares it and 307s to the corrected URL on mismatch (`base-server.js` ~L1414-1450). The interceptor bypasses this check, the Next-server fallback does not (F2). The Vary header OpenNext attaches is `RSC, Next-Router-State-Tree, Next-Router-Prefetch, Next-Router-Segment-Prefetch, Next-Url` (`cacheInterceptor.js` VARY_HEADER).
- **Key kinds to allow** (suggested regexes): html (no `rsc` header), `rsc` (`rsc: 1`, no prefetch header), prefetch (`next-router-prefetch: 1`), segment (`next-router-segment-prefetch` matching `^/[A-Za-z0-9_$.%~\-/]{1,200}$`). Any other `next-router-prefetch` value (Next also uses `2`) or malformed segment value: bypass.
- **Enable `enableCacheInterception: true`** in `open-next.config.ts` in the same plan that makes pages static (it runs after the proxy, see "Order" above). With D1 tag cache and Next 16 `nextMode`, `hasBeenRevalidated` and `isStale` add D1 reads per hit (subrequests, not CPU-heavy). A stale-from-tag entry makes the interceptor queue a DO revalidation (F8).

## ISR revalidation on workers.dev (item 5)

- Mechanism: with `queue: doQueue`, a stale entry (`isStale` from time or tag) makes the interceptor/server call `queue.send`, which calls `NEXT_CACHE_DO_QUEUE.get(idFromName(MessageGroupId)).revalidate(msg)`; the DO then runs `this.service.fetch("https://<host><url>", { method: "HEAD", headers: { "x-prerender-revalidate": <preview id>, "x-isr": "1" } })` through `env.WORKER_SELF_REFERENCE` and requires status 200 plus `x-nextjs-cache: REVALIDATED`, retrying with backoff (`DOQueueHandler`, 10 s timeout, up to 6 retries) [VERIFIED: `@opennextjs/cloudflare/dist/api/durable-objects/queue.js`]. The service binding in `wrangler.jsonc` already exists.
- With the gateway, that HEAD lands on the default entrypoint: hard-deny it (F8). The fill is a full render in a separate invocation (40-900 ms CPU) and can 1102 on Free; failures are retried, each a request against 100k/day. With F5 fixed (tags only, `revalidate: false`), time-based revalidation should almost never trigger; tag invalidation instead makes the next Pages fill regenerate in the foreground.
- The deploy warning: see F10. Verification recipe for spike (d): add a throwaway static test page with `export const revalidate = 60`, deploy, tail `clickit`, request it after 60 s, and expect (1) a `DOQueueHandler` invocation event, (2) a HEAD event on the default entrypoint, (3) the R2 object's `lastModified` changing (`wrangler r2 object` read-only, controller). If nothing happens, check the DO migration tag, that `DOQueueHandler` is exported from the module wrangler bundles as `main`, and that `WORKER_SELF_REFERENCE` resolves; a third-party report says re-exports of DO classes through a chain are sometimes not preserved by workerd's introspection [CITED, single anecdotal source, LOW].
- On workers.dev the Cache API (`caches.open`) used by OpenNext's regional cache and queue cache is not functional (prototype finding in cpu-en-home.md); the regional-cache wrapper is harmless but gives no benefit there.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Shared-page cache storage, SWR, stale-if-error, tiering, request collapsing | A Cache API + R2 store in the Worker | Workers Cache on the `Pages` entrypoint | That is the whole point of the signed plan; prototype only as D-50 fallback |

## Common Pitfalls

### Pitfall 1: Cache fragmentation or 307 loops from router headers (F2)
**What goes wrong:** variants per `next-router-state-tree`, or a cached `307 ?_rsc=…`.
**Why:** `Vary` from OpenNext, `validateRSCRequestHeaders`.
**How to avoid:** forward `_rsc`/state-tree/`next-url` untouched, key without `_rsc`, delete `Vary` in the Pages wrapper, add it back at the gateway.
**Warning signs:** `Cf-Cache-Status: MISS` on every RSC navigation; Location headers containing `_rsc`.

### Pitfall 2: `/ar` never caches (F3)
**Why:** next-intl `syncCookie` sets `NEXT_LOCALE` when the cookie is absent and `getAcceptLanguageLocale(…) !== locale` (`middleware/syncCookie.js`).
**How to avoid:** wrapper drops `Set-Cookie`; gateway sets it from the URL locale when the request cookie differs. `/en` happens to work because the default fallback equals en.
**Warning signs:** `BYPASS` on all `/ar/*`.

### Pitfall 3: Invalidate silently does nothing (F1)
**Why:** called from the wrong entrypoint, or `ctx.cache` undefined (local).
**How to avoid:** RPC on `Pages`, guard, assert `success`, log `errors`, coverage test.

### Pitfall 4: Admin saves "work" in preview and not on workers.dev
**Why:** the local runtime cannot cache or purge.
**How to avoid:** treat preview as logic-only; the invalidation/purge/hit/miss tests run in the controller's workers.dev deploy (spike e), with a probe route whose body shows a timestamp.

### Pitfall 5: Time-based ISR re-renders on Free (F5)
Set `revalidate: false` on public `unstable_cache` calls used by static routes; verify `initialRevalidateSeconds` is false/1 year in `prerender-manifest.json`.

### Pitfall 6: Per-visitor data leaks into a shared entry
**How to avoid:** the strip list is defence in depth; the real guard is D-24 (import graph) and the "byte-identical anon HTML" test. Also check any inline JSON (`NextIntlClientProvider` messages are fine), `Set-Cookie`, `Link`, absolute `Location`, metadata `alternates` built from host (Pitfall in F3). `metadataBase` is `siteUrl()` from env, not host [VERIFIED: `[locale]/layout.tsx`].

### Pitfall 7: Class `user` without a gate-equivalent render
`proxy.ts` for `anon` on `/watch/*` etc. returns 307 to `/auth?next=…` (`authAllowSkip` off) or the page (on). A cached anon 307 depends on `getAppConfig().authAllowSkip` and `flags.comingSoonMode`; flipping either in admin must purge, not invalidate (extend D-23's coming-soon rule to `auth_allow_skip`). The `Location` host issue applies.

### Pitfall 8: Gateway reads the wrong env
`next-env.mjs` is empty; `NEXT_PUBLIC_*` are inlined. Use the generated gateway config file; add a unit test that the cookie name derives identically to supabase-js (`sb-<first hostname label>-auth-token`; local stack hostname `127.0.0.1` gives `sb-127-auth-token`).

### Pitfall 9: Cache-Tag source
OpenNext's interceptor deletes `x-next-cache-tags` from served headers; compute tags yourself. Over-tagging is cheap (invalidation is lazy per entry and SWR serves stale), under-tagging shows stale pages. Include `site-config` on every page (footer, ticker, layout read it).

### Pitfall 10: Hit path pays startup cost
Keep gateway modules tiny; `./.open-next/worker.js` stays a dynamic import inside `Pages.fetch` only (prototype did the same). Static import of `.open-next/worker.js` evaluates the 2.6 MB proxy bundle in every isolate, including the gateway's.

### Pitfall 11: Scheduled publishing and the coming-soon episode gate
`isEpisodeLive(status, publish_at)` is time dependent; a static page will not flip at `publish_at`. The `publish-scheduled` cron does `updateTag` + `revalidatePath` but crons are off until the Phase 3 cutover (`"crons": []`); add the edge invalidate there too and note the gap until cutover.

### Pitfall 12: Clean-clone build with placeholder env
Making pages static means `next build` now executes their data reads. With the placeholder URL they must not throw; `generateStaticParams` must return `[]` on error. A build made that way must not be deployed (deploy guard).

### Pitfall 13: PLAT-03 (edit visible within 10 s) and `check-revalidate.mjs`
With invalidate + SWR the first request after a save returns the old copy (`UPDATING`) and triggers the refill; the second request within seconds shows the new copy if the fill succeeds. On Free the fill can 1102, leaving the old copy indefinitely. Update the script/expectation (poll twice, accept `UPDATING`) and report the residual risk.

### Pitfall 14: `scripts/cf/measure-routes.mjs` does not exist
CONTEXT.md says to reuse its patterns; `git log --all -- scripts/cf/measure-routes.mjs` is empty (02-21 planned it, the measurement was done by hand). `/Users/koss/.clickit-checks/perf-measure.sh` is Lighthouse-based. Write `scripts/cf/seed-cache.mjs` and a tail-sampling helper new, with the method from 02-CPU-REPORT (interleaved routes, 1 s apart, nearest-rank percentiles over `outcome: ok`, `exceededCpu` counted apart).

### Pitfall 15: User-class seeding needs a real session
A `user` key can only be filled by a request with a valid ES256 session cookie (02-CPU-REPORT referenced `make-session-cookie.mjs` and "approve measurement sign-ins"; neither is in the repo). Either Koss approves a measurement account (controller step, token expires hourly) or user keys fill on the first real signed-in visit. With F7 option B the HTML is identical, so only the class-gated redirects differ.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes (edge session verification) | ES256 via Web Crypto against the project JWKS; reject non-ES256, require `kid`, `exp`, `sub`; never treat cookie presence as a session |
| V3 Session Management | yes | Refresh stays in browser client + proxy on bypass; no rotation on hits |
| V4 Access Control | yes | Hard deny for `/admin*`, actions, `/api`, `/auth/callback`; admin shell identical for admin and viewer, Admin menu entry from the browser (RLS), never cached |
| V5 Input Validation | yes | Allowlisted paths and query keys, segment-header regex, `getSafeAuthNextPath`, drop untrusted `x-clickit-*` |
| V6 Cryptography | yes | Web Crypto only; no hand-rolled signature code |
| V8 Data protection | yes | No per-visitor data in shared entries (strip + import-graph + byte-identical test) |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Forged `sb-*` cookie to reach the user shell | Spoofing | Signature verification; name derived from config; forged value yields anon or bypass |
| `alg` confusion / HS256 or `none` token | Spoofing | Accept exactly ES256 with a JWKS kid; anything else bypasses (auth-js falls back to `getUser` for HS*; the gateway must not) |
| Unknown-kid flood forcing JWKS fetches | DoS | Refetch at most once per 60 s per isolate; cache CryptoKeys per kid |
| Cache poisoning via headers (Host, X-Forwarded-*, Forwarded, Next-Url, Accept-Language) | Tampering | Strip before `ctx.exports`; Workers Cache already keys on forwarded-host family; poisoning test; relative `Location`, no `Link` |
| Cache deception (user HTML stored under an anon key) | Info disclosure | Class in key, verified class, strip Cookie, Pages cannot be reached externally (default entrypoint only has a route; a non-default entrypoint is not addressable from the internet) [ASSUMED: workers.dev routes only to the default export] |
| Open redirect via `next` | Tampering | `getSafeAuthNextPath`; if moved client-side, same function in the browser |
| Stored 5xx or error page | Availability | 404/500 forced to `no-store` by OpenNext; wrapper no-store for anything else; 5xx never cached |
| Spoofed ISR header to force revalidation | Tampering | `x-prerender-revalidate` requires the build's preview id; gateway sends it direct, never cached |
| Stale entries after a security-relevant setting change (coming-soon, auth skip) | Info disclosure | Purge, not invalidate, for those toggles |
