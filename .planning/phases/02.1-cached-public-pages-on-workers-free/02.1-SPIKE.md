Payload sizes per route are the same in both builds: HTML 6484 / 6981 B, rsc = prefetch = `/_full` 3968 / 4382 B, `/_tree` 262 / 306 B, `__PAGE__` 3192 / 3413 B. The hashes differ between the two builds because the build ids differ; the comparison is within one build.

Finding F2 (RSC without `_rsc`):
- Interception off: an `rsc: 1` GET without `_rsc` answers **307 to `<route>?_rsc`** (Next's `validateRSCRequestHeaders`).
- Interception on: the same request answers **200**, because interception serves it before that check.
- A real client always sends `_rsc`, so cached RSC answers must be keyed with `_rsc` stripped or with the hash kept as Next computes it. Plans 02.1-02 and 02.1-06 must not serve an RSC body to a request whose `_rsc` does not match its headers, or Next's own 307 contract is lost.

Script fix found while preparing the run (Rule 1): the WIP state tree had a boolean at index 4. Next 16.4.2's `flightRouterStateSchema` accepts only a number or null there, so every state-tree variant would have been a parse error instead of a payload comparison. This was verified against Next's own parser; the fix is in commit f83cbdd.

### Misses on the spike deploy (controller question 2)

A miss is a full render.
- **`miss-render`**: 10 samples per route, unique `?spike_b`, 1 s apart, UTC window 2026-10-26T16:26:06.947Z .. 16:27:09.771Z. Result: **50 / 50 exceededCpu**, client 503 on all 50. The routes were /en/portfolio, /en/about, /en/privacy, /en/auth and /ar/portfolio.
- **`proto-hits`**: 20 GETs of `/en/about` with no query, 1 s apart, after more than 120 s idle (first visit after expiry of the prototype anon cache), UTC window 16:30:09.825Z .. 16:30:36.716Z. Result: **20 / 20 exceededCpu**, client 503. The first-visit fill never succeeded, so no later request got a hit.
- **During the page-view burst** (16:14-16:23): the prototype's first-visit misses on `/en/portfolio` answered 200 four times out of five (views 1, 3, 5, 8). View 10's miss got 503. Those ok renders cost up to 1,159 ms CPU.

Every exceededCpu event in tail reports `cpuTime: 10`, the cap. Yet many ok invocations ran far above 10 ms: ok full renders on 7222dcee had a p50 of 31-48 ms, and ok renders and media proxies in the page-view window reached 1,159 ms.

The limit is therefore not a plain 10 ms per request. It looks like an allowance that runs out:

| 2-minute buckets (UTC) | Heavy invocations (> 10 ms) |
|---|---|
| until 16:12 | almost all ok |
| 16:14-16:22 (page views, each with about 3.7 video range requests through `/api/cdn/storage` at about 0.9-1.5 s CPU) | mixed |
| 16:26-16:31 | 0 ok, 70 exceededCpu |

This is an observation; the mechanism is not proven.

How often a miss gets 1102:
- 7222dcee: 64 of 150 full renders (43%), plus 1 exceededMemory and 4 canceled.
- Spike version: 70 of 70 in the last window. In the page-view window: 1 of 5 document misses, and 28 of 37 `/api/cdn/storage` requests.

Hit CPU, for comparison:
- Workers Cache hit: gateway 0-2 ms (n = 50, p50 0); SpikeProbe not invoked.
- Prototype `HIT-EDGE` document: p50 6 ms.
- ISR read via interception: p50 9 ms.

**b verdict: NEEDS-CONTROLLER**, with these numbers. The signed plan set no threshold. The data say a cold fill (a miss) fails often on Free (43% on 7222dcee; 100% once the allowance seems spent), so the design cannot rely on a viewer's request filling the cache.

The real session came from a throwaway confirmed user, created on the local stack through the admin API, signed in with a password grant and deleted afterwards (admin API answered 200). Its token is ES256 with a kid from the local JWKS. The cookie value is 2589 bytes; the file was mode 600, outside the repo and deleted. The anon bodies for no cookie, forged cookie and verifier-only are byte-identical.

Header variants per route: baseline, then a repeat of the baseline, `Accept-Language: ar`, `Cookie: NEXT_LOCALE=ar; sb-x=1`, a mobile User-Agent, `X-Forwarded-Host: evil.example`, `Forwarded: host=evil.example` and `Next-Url: /en/watch`.

- **Run 1** (no warm-up, the first requests after the preview start):
  - `/spike-probe/a`, `/ar/portfolio` and `/en/about` were identical across all variants.
  - `/en/portfolio` and `/en/auth`: the very first request (the baseline) differed from every later request, and the later requests matched each other, so the baseline-repeat differed too. The causes were Suspense streaming order (`<!--$?-->` fallback vs resolved) and script chunk order.
  - On `/en/portfolio` the cookie variant also differed, and on `/en/privacy` the Accept-Language variant did. Both differences were in streamed boundary order.
  - None of these differences is caused by a header. The X-Forwarded-Host, Forwarded and Next-Url bodies had the same hash as the baseline-repeat, and the cookie and Accept-Language headers were stripped before the render. They are cold-isolate render-order effects.
- **Run 2** (`spike-local-c2`, 2026-10-25T21:43:02Z and 21:43:05Z): `--warmup 2`, two full passes. Every route was byte-identical across all 7 variants in both passes, and pass 1 equals pass 2 for every route:
  - `/spike-probe/a`
  - `/en/portfolio`
  - `/ar/portfolio`
  - `/en/about`
  - `/en/privacy`
  - `/en/auth`

  So there is no header-driven difference on these routes, and none from X-Forwarded-Host, Forwarded or Next-Url.
- `/en/auth` HTML has no per-request token: no `nonce=`, no CSRF field, and it is identical across passes. Limitation: the local build has no `NEXT_PUBLIC_TURNSTILE_SITE_KEY`, so the Turnstile widget markup is absent locally. The Turnstile token is produced in the browser, not in server HTML.
- RTL: `/ar/portfolio` has `lang="ar" dir="rtl"`; `/en/*` has `lang="en" dir="ltr"`.
- The expected User-Agent cause (`getIsMobile` in the landing hero) did not show on these six routes. The plans that touch device-dependent markup (02.1-05 media, 02.1-08 to 02.1-18 pages) still own it for the routes that use it.

Finding: renders right after an isolate start are not byte-deterministic (streaming order). A cache fill taken from a cold isolate is still a valid page, but byte-equality checks in later plans need a warm-up GET.
