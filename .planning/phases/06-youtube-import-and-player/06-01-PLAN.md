<objective>
Lay the data foundation and the key module for Phase 6, after proving the upstream phases are on the branch base.

Purpose: every later plan reads the new episode columns, calls `renumber_season` / `record_youtube_checks`, and reads the key through one resolver. The migration is split in two (expand before deploy, contract after "Test key" passes) because the deployed code reads the new columns; applying one combined migration after deploy (the RESEARCH order) would break import, the watch-page preflight and the cron on day one. Live apply of either file is owner-gated in plans 06-18 and 06-19, never here.

Output: two migration files with a text-level test, the key resolver with tests, `WorkerEnv.YOUTUBE_API_KEY`, `.env.example` placeholder, and regenerated `database.types.ts` (controller-run local apply).

Decisions needing Koss at the plan gate (implemented here, switchable or reviewable):
1. Renumber moves archived episodes to N+1..N+K (in archived order) so "1 to N" holds under the season-wide unique number constraint (RESEARCH Open Question 3). Alternative (leave archived numbers, fail on collision) is not built.
2. Two migrations instead of one: expand (columns, index, functions) approved and applied before deploy; contract (drop `youtube_api_key`) approved after "Test key" passes on live. Each is one approval.
3. If the controller's read-only duplicate check finds repeated `youtube_video_id` values on live, the expand migration aborts by design (guard block). Koss then picks which rows to clear (a live write, his word), before the migration is retried.
</objective>
