# Requirements - v2.3 Safe Ownership Transfer

**Milestone:** v2.3
**Total:** 24 requirements across 6 gated phases
**Generated:** 2026-05-18
**Mode:** gated handoff, no step advances without required details

---

## Gate Rules

- [ ] **GATE-01**: Every phase starts with a required-details checklist. Missing details stop the phase.
- [ ] **GATE-02**: No destructive transfer action happens until a tested rollback path exists.
- [ ] **GATE-03**: New-owner systems are verified with temporary URLs before the production domain moves.
- [ ] **GATE-04**: Secrets are never shared in chat or committed to git. They are entered directly into GitHub, Vercel, Supabase, or a password manager.

## Ownership Intake

- [ ] **OWN-01**: Confirm recipient name, email, GitHub username or organization, Vercel team or account slug, Supabase organization, and domain registrar access owner.
- [ ] **OWN-02**: Confirm transfer model: full ownership transfer, collaborator handoff first, or new-account clone with later shutdown.
- [ ] **OWN-03**: Confirm maintenance window, rollback window, and who has authority to approve DNS cutover.
- [ ] **OWN-04**: Inventory current production state: GitHub repo, Vercel project, Supabase project, custom domains, env vars, cron routes, storage buckets, auth providers, and third-party services.

## GitHub Handoff

- [ ] **GH-01**: Recipient has accepted GitHub access and can clone the repo.
- [ ] **GH-02**: Recipient can push a harmless branch and open a test PR, or the transferred repo is visible in their organization.
- [ ] **GH-03**: Branch protection, default branch, repository secrets, deploy keys, and app permissions are documented or recreated.
- [ ] **GH-04**: Original repo remains available until new production is verified.

## Supabase Migration

- [ ] **SB-01**: Recipient Supabase project exists and project ref, region, organization, and billing state are confirmed.
- [ ] **SB-02**: Schema, migrations, RLS policies, functions, triggers, and generated TypeScript types are migrated and verified.
- [ ] **SB-03**: Production data is exported and imported with row counts checked for critical tables.
- [ ] **SB-04**: Storage buckets, object paths, public/private settings, and signed-upload behavior are migrated and verified.
- [ ] **SB-05**: Auth settings, redirect URLs, email templates, OAuth providers, admin user, and app_config are recreated and verified.
- [ ] **SB-06**: Old Supabase project stays online during the rollback window.

## Vercel Migration

- [ ] **VC-01**: Recipient Vercel project is connected to the recipient GitHub repo and deploys from the intended default branch.
- [ ] **VC-02**: All required environment variables are recreated in Production, Preview, and Development scopes as needed.
- [ ] **VC-03**: Preview deployment builds successfully and loads core pages against the recipient Supabase project.
- [ ] **VC-04**: Production deployment reaches Ready before any custom domain changes.
- [ ] **VC-05**: Cron routes, deployment protection, framework settings, Node version, and project aliases match the working project.

## Domain Cutover

- [ ] **DNS-01**: Current DNS records are captured before edits.
- [ ] **DNS-02**: New Vercel project has the custom domain added and verified before nameserver or record changes.
- [ ] **DNS-03**: DNS cutover is done only after GitHub, Supabase, Vercel, and preview verification pass.
- [ ] **DNS-04**: Production domain returns 200 for `/en/portfolio`, `/en/watch`, `/en/auth`, `/robots.txt`, and `/sitemap.xml`.

## Final Verification

- [ ] **VERIFY-01**: Viewer flow works: portfolio, watch page, series page, search, coming soon, support.
- [ ] **VERIFY-02**: Auth flow works: sign in, sign out, reset-password page, admin routing.
- [ ] **VERIFY-03**: Admin flow works: create/edit show, upload artwork, upload hero video, create/edit episode, archive/restore.
- [ ] **VERIFY-04**: Supabase data, storage URLs, auth redirects, and Vercel env vars all point to the recipient-owned accounts.
- [ ] **VERIFY-05**: Old accounts are kept as rollback for the agreed window, then access is reduced or removed.

## Out of Scope

| Item | Reason |
|---|---|
| Deleting old accounts during migration | Rollback needs the old production stack alive |
| Sharing service-role keys in chat | Security risk |
| Moving DNS before preview verification | Highest chance of downtime |
| Changing app features during transfer | Increases blast radius |
| Rebuilding architecture | Transfer milestone, not product redesign |
