# Roadmap - v2.3 Safe Ownership Transfer

**Milestone:** v2.3 Safe Ownership Transfer
**Status:** Planned, blocked on required transfer details
**Generated:** 2026-05-18

## Principle

No big-bang transfer. Clone, verify, cut over, then retire.

The old production stack stays alive until the new owner's stack passes verification and the agreed rollback window ends.

## Phase 35: Ownership Intake and Transfer Packet

**Goal:** Lock the exact transfer model, owners, access, rollback window, and inventory before touching production.
**Depends on:** None
**Requirements:** GATE-01..04, OWN-01..04

**Required details before phase can start:**
1. Recipient GitHub, Vercel, Supabase, and domain registrar identities
2. Transfer model: collaborator-first, full transfer, or clone-and-cutover
3. Maintenance window and rollback window
4. Secret handoff method outside chat
5. Current account owners and project IDs

**Success criteria:**
1. `.planning/milestones/v2.3-REQUIREMENTS.md` Required Details Form is filled.
2. Current production inventory lists GitHub repo, Vercel project, Supabase project, env vars by name, buckets, auth settings, custom domains, cron routes, and third-party services.
3. Rollback owner and rollback steps are named.
4. No account transfer or DNS edit has happened yet.

**Blocked if missing:** any recipient account identity, domain registrar access, or secret handoff method.

## Phase 36: GitHub Handoff

**Goal:** Give the recipient working code ownership without breaking current production.
**Depends on:** Phase 35
**Requirements:** GH-01..04

**Required details before phase can start:**
1. Recipient GitHub username or organization
2. Decision: transfer existing repo or clone to new repo
3. Default branch name
4. Required branch protection rules

**Success criteria:**
1. Recipient can clone the repo.
2. Recipient can push a test branch or the transferred repo is visible in their account.
3. Default branch and protection rules match the intended workflow.
4. Original repo remains available for rollback until final verification.

**Blocked if missing:** recipient GitHub acceptance or target repo owner.

## Phase 37: Supabase Migration

**Goal:** Recreate the backend in the recipient Supabase account and prove data, storage, auth, and admin access work before Vercel uses it.
**Depends on:** Phase 36
**Requirements:** SB-01..06

**Required details before phase can start:**
1. Recipient Supabase organization and project ref
2. Region and billing plan
3. Database password or connection method
4. Auth redirect domains
5. Admin user email
6. Storage bucket list

**Success criteria:**
1. Schema, RLS policies, triggers, functions, and migrations are present in recipient Supabase.
2. Critical table row counts match current production.
3. Storage buckets and important object paths work, including `site-assets`.
4. Auth settings and redirect URLs point to temporary Vercel URLs first.
5. `app_config.admin_user_id` points to the recipient-approved admin user.
6. New `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` are ready for Vercel.

**Blocked if missing:** recipient Supabase project, admin user, or safe secret-entry path.

## Phase 38: Vercel Migration

**Goal:** Deploy the app in the recipient Vercel account against the recipient Supabase backend, using a temporary URL first.
**Depends on:** Phase 37
**Requirements:** VC-01..05

**Required details before phase can start:**
1. Recipient Vercel account or team slug
2. Recipient GitHub repo URL
3. Full env var list and values entered directly into Vercel
4. Intended production branch
5. Deployment protection decision

**Success criteria:**
1. Recipient Vercel project deploys from the recipient GitHub repo.
2. Production, Preview, and Development env vars are present where needed.
3. Preview deployment returns 200 on `/en/portfolio`, `/en/watch`, `/en/auth`, `/robots.txt`, and `/sitemap.xml`.
4. Admin sign-in and media upload work against recipient Supabase.
5. Production deployment reaches Ready before domain cutover.

**Blocked if missing:** Vercel env vars, GitHub connection, or recipient Supabase keys.

## Phase 39: Domain Cutover

**Goal:** Move the production domain only after the new stack is already proven through temporary URLs.
**Depends on:** Phase 38
**Requirements:** DNS-01..04

**Required details before phase can start:**
1. Domain registrar login owner
2. Current DNS records export
3. New Vercel domain verification instructions
4. Cutover window
5. Rollback DNS records

**Success criteria:**
1. New Vercel project has the production domain added and verified.
2. DNS records are changed during the approved window.
3. Public DNS resolves to the new Vercel target.
4. Production domain returns 200 for the core verification URLs.
5. Old Vercel and Supabase remain online for rollback.

**Blocked if missing:** registrar access, DNS backup, or approved cutover window.

## Phase 40: Final Verification and Access Cleanup

**Goal:** Prove the recipient-owned production stack works end to end, then reduce old-owner access only after the rollback window.
**Depends on:** Phase 39
**Requirements:** VERIFY-01..05

**Required details before phase can start:**
1. Rollback window end time
2. Recipient production approver
3. Access removal policy
4. Final smoke-test checklist owner

**Success criteria:**
1. Viewer, auth, admin, upload, storage, and cron paths are tested on the production domain.
2. Vercel env vars point only to recipient-owned Supabase where intended.
3. Supabase auth redirects include the final production domain.
4. Recipient confirms they can deploy without you.
5. Old-owner access is reduced only after the rollback window ends.

**Blocked if missing:** final approver or rollback window agreement.

## Dependency Graph

```
35 (Ownership Intake)
  -> 36 (GitHub Handoff)
  -> 37 (Supabase Migration)
  -> 38 (Vercel Migration)
  -> 39 (Domain Cutover)
  -> 40 (Final Verification)
```

No phase runs in parallel. This is ownership migration, not feature work.
